# Клиенты и рассылки

Локальное приложение для сбора контактов, аудиторий и подготовки рассылок. Django 5.2, Python 3.11+, SQLite или PostgreSQL. Интерфейс находится в prototype/dist.

## Состояние

Подключены сборщики Goszakup, e-ondiris, Gov.kz, ДФО и Kaspi, аудитории, фильтры, карточки клиентов, история источников и проверка email. Проверка DNS не подтверждает существование ящика. Отправка сообщений пока не подключена. Kaspi: автоматический обход 10 категорий компьютеров/комплектующих, первый город Алматы, с очередью и паузой. Подробности: [docs/KASPI_AUTOMATIC.md](docs/KASPI_AUTOMATIC.md).

Over-shop.kz: локально загружены 5750 аккаунтов и перенесены 79 подписок; ещё 16 контактов созданы для подписчиков вне загруженной клиентской базы. Сохранены ID, сегменты покупок, даты, рубрики и исходные флаги подписки. Постоянная синхронизация не подключена. Классические подписки сайта и Email-маркетинг — разные источники статусов; регистрация и покупка не подтверждают согласие на рекламу. Порядок переноса на сервер: [docs/OVER_SHOP_IMPORT.md](docs/OVER_SHOP_IMPORT.md). Данные передаются отдельно от GitHub.

## Локальный запуск

```powershell
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt
.venv/Scripts/python manage.py migrate
.venv/Scripts/python manage.py runserver 127.0.0.1:8173 --noreload
```

Для повторного локального запуска на Windows: `& .\scripts\start_local.ps1`.
Скрипт находит проект относительно своего файла, проверяет конфигурацию и миграции,
запускает только веб-приложение на 127.0.0.1:8173 и отключает SMTP. Это ручной
локальный запуск; автозапуск ОС и production-службу он не устанавливает.

Приёмка локальной копии и оставшийся пункт настоящей перезагрузки ОС:
[docs/STAGE_GENERAL_ACCEPTANCE_2026_11_13.md](docs/STAGE_GENERAL_ACCEPTANCE_2026_11_13.md).

Локальный автозапуск Windows удалён 13.11.2026. Ручной запуск сохранён.
Для сервера подготовлены Linux/systemd, Gunicorn и защищённый профиль без SMTP:
[инструкция агенту](docs/SERVER_AUTOSTART.md), [служба](deploy/systemd/over-sales.service).
Установка и фактическая перезагрузка сервера ещё не проверены.

База: data/contacts.sqlite3. Не удалять data/ при обновлении. POSTGRES_DB, POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_HOST, POSTGRES_PORT включают PostgreSQL, но сами не переносят данные.

Отдельные процессы: `manage.py collect_contacts`, `collect_producers`, `collect_gov`, `collect_dfo`, `collect_kaspi`, `check_emails`. Управление паузой — в интерфейсе. Проверки: `manage.py test contacts`.

Приватная БД, выгрузки, скриншоты, окружение и исторические рабочие отчёты не публикуются. Примеры в fixtures — демонстрационные. Для Over-shop нужны собственные разрешённые выгрузки; пути по умолчанию в скриптах относятся к локальному окружению и должны быть заменены аргументами нужных файлов.

## Развёртывание

Задание агенту: [docs/DEPLOYMENT_AGENT_TASK.md](docs/DEPLOYMENT_AGENT_TASK.md). Создать серверную БД, запустить автоматическое пополнение, развернуть sales.overclockers.kz и добавить «Рассылки» в меню p1.overclockers.kz. Ручной перенос локальной базы и ожидание полного наполнения не обязательны. Over-shop требует отдельного подключения и автоматически из GitHub не заполнится.

**Вход обязателен для приложения и закрытых API.** Для первой учётной записи выполните `python manage.py prepare_auth_setup`, самостоятельно скопируйте одноразовый код из `data/private/account-setup-code.txt` в форму `/setup/` и задайте логин и пароль (минимум 12 символов). Код действует 24 часа, используется один раз и не выводится в консоль. Файл с кодом не должен попадать в Git. Повторная первоначальная настройка после создания пользователя запрещена.

Администратор управляет пользователями и назначает роли через `/accounts/`; каждый пользователь может изменить собственный пароль. Новые и прежние обычные пользователи без назначения получают роль «Наблюдатель». Менеджер управляет клиентами, импортом/экспортом, аудиториями, шаблонами и имитациями рассылок; редактор изменяет шаблоны и просматривает рабочие данные; наблюдатель только просматривает рабочие данные без экспорта. Источники, подключения и управление пользователями доступны только администратору. Разделения видимости клиентов между сотрудниками нет. Сервер проверяет права на каждом запросе; неизвестные API закрыты для обычных ролей. Свою роль и роль первого администратора менять нельзя. Назначение роли записывается в журнал; новые права действуют на следующем запросе уже открытой сессии (интерфейс обновляется при перезагрузке). Реальная отправка запрещена для всех ролей, включая администратора.

Действия в журнале привязаны к вошедшему пользователю. Публичные ссылки подтверждения подписки, отписки и отслеживания работают без входа. Самостоятельная регистрация и восстановление пароля по email не включены.

Перед запуском имитации требуется согласование: в «Рассылках» нажмите «Согласование», передайте сохранённую версию на проверку, затем администратор одобряет её или возвращает с комментарием. При изменениях письма и настроек согласование снимается; перед решением и первоначальным запуском проверяется и состав получателей. Изменённое одобрение не подходит для продолжения старого запуска. Решения сохраняются в журнале. Подробности — `docs/STAGE_CAMPAIGN_APPROVAL.md`. Реальная отправка остаётся запрещённой.

Колокольчик в шапке открывает уведомления об ошибках, остановках и согласовании. Прочтение индивидуально для пользователя; повторные ошибки одного запуска группируются. При развёртывании после миграций выполните `python manage.py sync_app_notifications` и перезапустите приложение и фоновые процессы. Команда переносит существующую историю, без запуска задач и отправки писем. Подробности — `docs/STAGE_INTERNAL_NOTIFICATIONS.md`.

Перед публикацией настройте production-сервер, HTTPS, секреты, резервные копии и `SALES_SECURE_COOKIES=1`. Локально используйте `0`. Cookie приложения имеют отдельные имена `sales_sessionid` и `sales_csrftoken`. Для форм применяется `Referrer-Policy: same-origin`: источник сохраняется внутри приложения для CSRF-проверки, но не передаётся на другие сайты. Реальные рассылки не запускать при развёртывании.


### Редактор: AI, персонализация и проверки

Персонализация: `{{name|клиент}}`, `{{company|вашей компании}}`, `{{city|вашем городе}}`, `{{email}}`. Запасное значение после `|` применяется при пустом поле. `{{unsubscribe_url}}` — служебная переменная: в предпросмотре демонстрационный адрес, при отправке понадобится индивидуальная рабочая ссылка. Подстановка не выполняет Python, JavaScript или выражения Django. HTML-значения экранируются.

Проверки выполняются локально кнопкой в редакторе: тема, переменные, отписка, небезопасные/пустые/относительные ссылки, активный HTML, alt, размер и незаполненные заготовки. Сайты по ссылкам не опрашиваются. Это не проверка доставки или гарантия отсутствия спама. Черновики можно сохранять с замечаниями; реальная отправка не подключена.

Для AI задайте в окружении процесса `OPENAI_API_KEY` и `SALES_AI_MODEL` (идентификатор доступной вам модели с Responses API и Structured Outputs), затем перезапустите Django. Один только файл .env автоматически не читается. Ключ не хранится в БД, JS или Git. Без настройки панель показывает статус «не настроен», локальные функции доступны. Используется https://api.openai.com/v1/responses с store=false; официальная схема: https://developers.openai.com/api/reference/resources/responses/methods/create .

AI получает только введённые задание и исходный текст, без чтения клиентской БД и данных примера. Нет автоматического применения, сохранения или рассылки. Результат можно просмотреть и изменить, затем применить к теме, прехедеру, выбранному текстовому блоку или новому блоку. Если шаблон/выбор блока изменился во время запроса, применение блокируется. Квота хранится в БД: 30 попыток в сутки приложения, пауза 10 секунд; неудачные вызовы также учитываются. Модель и подключение должен настроить администратор; интеграционные тесты используют имитацию API и не расходуют средства.


### Тестовая отправка SMTP

В редакторе появился раздел «Тестовая отправка email»: выбирается один адрес из серверного списка `SALES_TEST_RECIPIENTS`, отправляется текущий черновик (сохранение в БД не требуется) и данные примера персонализации. Система не обращается к аудиториям и не запускает массовую отправку. Тема помечается `[ТЕСТ]`, письмо содержит уведомление о тесте, ссылка отписки заменяется неактивным текстом. Отслеживания открытий, переходов и доставки пока нет.

Параметры окружения перечислены в `.env.example`. Сам файл не загружается автоматически. До настройки `SALES_SMTP_ENABLED=1`, хоста, отправителя и разрешённых тестовых адресов кнопка отключена. Используйте ровно один режим: STARTTLS (`EMAIL_USE_TLS=1`, `EMAIL_USE_SSL=0`, обычно порт 587) или SSL (`EMAIL_USE_TLS=0`, `EMAIL_USE_SSL=1`, обычно 465); точные порт и режим берутся у провайдера. Если указан логин, нужен пароль. Ключи и пароли не вводятся в интерфейсе и не должны попадать в Git. После настройки перезапустите Django. Универсальный SMTP подходит в том числе для Amazon SES с отдельными SMTP-учётными данными SES.

Перед отправкой выполняются локальные проверки шаблона; ошибки блокируют тест, замечания показываются отдельной проверкой. Письмо содержит HTML и текстовую альтернативу. Статус «Принято SMTP» не означает доставку во входящие. Реальные настройки домена SPF/DKIM/DMARC проверяются отдельно после выбора провайдера.

Результаты последних тестов хранятся в локальной БД. Идентификатор попытки сохраняется в этой вкладке; повтор того же запроса не отправляет письмо снова. Для ещё одного идентичного письма нажмите «Новый тест». При сетевом сбое результат может быть неизвестен: проверьте почту и журнал провайдера перед новым тестом. Если процесс прервётся после передачи письма, запись останется «Результат пока не подтверждён»; автоматически повторять её нельзя. Лимиты для всего приложения: 10 секунд между попытками и 30 попыток за последние 24 часа. Автоматических повторов нет. Регрессионные тесты используют локальный почтовый backend и не отправляют реальные письма.

Очередь рассылок пока работает только в имитации: `python manage.py process_campaign_queue` (отдельный процесс рядом с сервером). Управление: «Рассылки» → «Очередь (имитация)». Подробности и приёмка: docs/STAGE_DISPATCH_QUEUE_SIMULATION.md. Настройки SMTP не включают реальную отправку в этом обработчике.

Центр подписок: меню «Подписки», подтверждение и веб-отписка по ссылкам без отправки писем. Тестовые записи изолированы; рабочая отписка блокирует email во всех аудиториях. Для публичных ссылок после переноса задайте SALES_PUBLIC_BASE_URL. При обновлении перезапускайте сервер и обработчики очередей. Подробности: docs/STAGE_SUBSCRIPTION_CENTRE.md.
# Servercore: проверка подключения и собственных ссылок

Локально реализован подэтап без отправки: меню **Настройки → Servercore и учёт событий**.
Описание, параметры окружения, сценарий проверки и ограничения — [docs/STAGE_SERVERCORE_TRACKING.md](docs/STAGE_SERVERCORE_TRACKING.md).

В разделе «Рассылки» доступны проверка письма и собственная статистика конкретной рассылки, без отправки.
Сценарий приёмки — [docs/STAGE_CAMPAIGN_MAIL_CHECK.md](docs/STAGE_CAMPAIGN_MAIL_CHECK.md).

В меню «Сценарии» реализована имитация автоматических цепочек для активных/пассивных аудиторий:
условия, задержки, ограничения частоты, пауза, продолжение и журнал.
Описание и приёмка — [docs/STAGE_AUTOMATION_SCENARIOS_SIMULATION.md](docs/STAGE_AUTOMATION_SCENARIOS_SIMULATION.md).

В меню «Репетиции» сценарии связаны с проверками, персонализацией, подготовкой письма и собственными событиями открытия, перехода и отписки.
Отдельные часы, снимки тестового источника и журнал позволяют проверить цепочку без SMTP и изменений рабочей базы.
Сценарий приёмки — [docs/STAGE_END_TO_END_REHEARSAL.md](docs/STAGE_END_TO_END_REHEARSAL.md).

В «Репетициях» доступны тестовые ошибки доставки и жалобы: ограниченные повторы с задержкой,
запрет дальнейших шагов получателя и история каждой условной попытки. Без SMTP и изменений рабочей базы.
Подробности — [docs/STAGE_REHEARSAL_DELIVERY_ERRORS.md](docs/STAGE_REHEARSAL_DELIVERY_ERRORS.md).

В «Репетициях» добавлена автоматическая остановка по настраиваемым порогам ошибок и жалоб:
минимальная выборка, доли по каждой рассылке, остановка следующих шагов и повторов, сохранённая причина.
Тестовый режим и приёмка — [docs/STAGE_AUTOMATIC_CAMPAIGN_STOP.md](docs/STAGE_AUTOMATIC_CAMPAIGN_STOP.md).

В меню «Частота» реализован общий контроль по email между рассылками и сценариями:
минимальный интервал, скользящие суточный/недельный лимиты, общие тестовые часы и история причин ожидания.
Без SMTP и изменений рабочей базы. Приёмка — [docs/STAGE_SHARED_TEST_FREQUENCY.md](docs/STAGE_SHARED_TEST_FREQUENCY.md).

Меню «Журнал действий»: автор, создание/изменение рассылки, управление тестовыми запусками,
системные остановки, результаты и снимки до/после. Действия привязаны к авторизованному пользователю.
Приёмка — [docs/STAGE_ACTION_AUDIT_JOURNAL.md](docs/STAGE_ACTION_AUDIT_JOURNAL.md).
