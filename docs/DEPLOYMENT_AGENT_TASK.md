# ТЗ агенту: развёртывание Sales из GitHub

## Результат

Развернуть проект https://github.com/diawar/sales из ветки `main` по адресу **https://sales.overclockers.kz**. В меню **https://p1.overclockers.kz** добавить пункт **«Рассылки»**, ведущий на этот адрес. Поддомен `sales` трактуется как `sales.overclockers.kz` по основному домену заказчика.

**Последнее уточнение заказчика: главное — создать серверную БД и запустить автоматическое пополнение.** Первоначально БД может быть пустой: ждать полного сбора для сдачи развёртывания не требуется. Обязательный ручной перенос локальной базы и выгрузок исключён из задачи.

Не считать публикацией запуск Django runserver. Нужна работа после перезагрузки сервера, защищённый доступ к данным и подтверждённая проверка функциональности. Работать по подэтапам ниже с остановками для проверки заказчиком.

## 1. Обследование и план

1. Проверить доступ к репозиторию, серверу, DNS overclockers.kz и исходникам/развёртыванию p1.overclockers.kz. Использовать предоставленные подключения; пароли не включать в Git, отчёты и чат.
2. Найти инструкции AGENTS.md, существующие механизмы деплоя, reverse proxy, TLS и авторизации. Определить ОС, ресурсы, занятые порты, каталоги, владельца процессов, способ резервного копирования. Соседние приложения не останавливать.
3. Проверить DNS для sales и доступность адреса сервера; не заменять существующие записи без проверки назначения. Не менять MX и SPF/DKIM/DMARC для этого развёртывания.
4. Прочитать README.md, это ТЗ и настройки Django; исторические рабочие отчёты не опубликованы. Получить SHA main и закрепить его в плане релиза. При обновлении main до запуска повторно проверить изменения.
5. Определить движок серверной БД, создать схему миграциями и настроить автоматические обработчики реализованных источников. Перенос приватного файла не является условием запуска. Документировать план, зависимости доступа и откат, затем остановиться для проверки.

## 2. Подготовка приложения к серверу

Текущий стек: Python 3.11+, Django 5.2, requirements.txt; интерфейс уже находится в prototype/dist и обслуживается разрешёнными статическими маршрутами Django. SQLite — data/contacts.sqlite3, опционально PostgreSQL через POSTGRES_*; наличие этих переменных само по себе не переносит данные.

**Критическое условие:** текущая версия рассчитана на localhost и не имеет пользовательской авторизации. До открытия публичного доступа закрыть и UI, и **все /api/**, экспорты, журнал и операции импорта/запуска сборщиков проверенным механизмом входа. Предпочесть совместимый существующий SSO/access gateway p1, если он есть. Иначе реализовать серверную авторизацию с сессиями и управляемыми аккаунтами; не ограничиваться скрытием кнопок. Не создавать самостоятельный публичный доступ к внутреннему upstream в обход защиты.

Настроить отдельные production-настройки, не ломая локальный запуск:

- DJANGO_SECRET_KEY — случайный постоянный секрет из защищённого окружения; production должен отказываться запускаться с локальным ключом по умолчанию.
- DEBUG=False; ALLOWED_HOSTS только нужные имена. Добавить `sales.overclockers.kz`, а не `*`.
- CSRF_TRUSTED_ORIGINS для HTTPS sales; защищённые cookies, корректная работа CSRF после проксирования и входа.
- HTTPS redirect и proxy SSL header только при доверенном reverse proxy, который очищает поддельные заголовки клиента. Настройки HSTS вводить после проверки сертификата, не включать includeSubDomains для всех сайтов без отдельной оценки.
- Production WSGI/ASGI-сервер с фиксированной версией зависимости, сервис под непривилегированным пользователем. `runserver` и prototype/server.cjs не использовать для production.
- Upstream слушает loopback/Unix socket; внешне доступны только необходимые HTTP/HTTPS, остальные порты закрыты.
- Данные, исходные выгрузки, окружение и резервные копии вне публичного web-root. Прокси не должен раздавать data/, .env, .git или произвольные файлы проекта.
- Не добавлять в логи содержимое клиентских выгрузок, email, телефоны, cookies и секреты; ротация логов обязательна.

Провести проверки на закрытом окружении и остановиться перед публикацией.

## 3. БД и состояние

Рабочая клиентская БД **не хранится в GitHub**. data/ исключена из Git, как и приватные промежуточные JSON Over-shop и скриншоты. Переносить только защищённым каналом, без коммита/публичных артефактов.

Если переносится существующая SQLite:

1. Согласовать короткую остановку приложения **и всех пишущих обработчиков** либо сделать согласованную online-backup средствами SQLite. Нельзя просто копировать активный sqlite3-файл, игнорируя WAL.
2. Проверить целостность резервной копии, контрольную сумму и восстановление. Сохранить исходную копию отдельно до миграций.
3. Поместить рабочие данные в постоянный каталог, который не удаляется при смене релиза, с ограниченными правами. Не размещать SQLite на сетевой ФС с неподдерживаемыми блокировками.
4. Выполнить миграции. Сверить числа клиентов, контактов, аудиторий, источников, отписок и курсоры сборщиков до/после. Не сбрасывать курсоры и не запускать повторный полный импорт.
5. При выборе PostgreSQL выполнить и проверить явный перенос данных и связей; заранее подготовить откат. Не делать переход побочным эффектом установки переменных.

Для чистой установки: `python -m venv .venv`, установка requirements.txt, `manage.py migrate`. Создать необходимые БД/роль/права и корневые аудитории, проверить миграции. Настроить и включить автоматическое пополнение из уже реализованных источников Goszakup, e-ondiris, Gov.kz и ДФО с сохранением происхождения и без дублей. Проверить первый успешный цикл/небольшую партию и продолжение фоновой очереди; полного наполнения ждать не нужно. Действующие разрешения и ограничения источников соблюдать; не предполагать новые доступы/API-ключи. Если конкретному источнику недостаёт доступа, отразить это отдельно; создание БД и работа остальных источников от него не зависят.

Перед массовой загрузкой каждого источника проверить ограниченную партию; после проверки продолжать с сохранённого курсора. Контроль заполнения: число уникальных клиентов, контактов, email, телефонов и аудиторий по каждому источнику, число отложенных/ошибочных записей, повторный запуск без дублей. При переносе сверить точные исходные количества; при сборе заново указать фактический охват и оставшуюся очередь. Не придумывать целевое число записей и не подменять реальные записи демонстрационными. Не удалять исходные данные и отписки.

Особенности Over-shop: локально загружены 5750 аккаунтов и 79 подписок, для ещё 16 подписчиков созданы отдельные контакты. Это не означает переноса на сервер: приватные выгрузки нужны отдельно от GitHub, команда импорта и миграция описаны в docs/OVER_SHOP_IMPORT.md. Постоянного соединения с сайтом пока нет. Есть отдельный классический модуль подписок; пустой журнал соглашений не означает отсутствие подписчиков. Не присваивать согласия массово.

## 4. Фоновые сервисы

Предусмотреть отдельные управляемые процессы с рестартом и журналами:

```text
python manage.py collect_contacts
python manage.py collect_producers
python manage.py collect_gov
python manage.py collect_dfo
python manage.py collect_kaspi
python manage.py check_emails
```

Проверить текущие аргументы команд в исходниках. Не запускать два конкурирующих экземпляра одного обработчика; сохранять встроенные leases, паузы и интервалы. После проверки миграций и конфигурации включить сбор. Перед запуском серверных обработчиков остановить локальные экземпляры или согласовать единственную активную установку. Не усиливать частоту запросов к источникам. Проверить запись heartbeat, продолжение курсора и действие кнопки «Пауза».

Kaspi по последующему запросу заказчика подключён локально: после обновления кода и миграции 0020 предусмотреть отдельную службу collect_kaspi и проверить её доступ к публичным запросам витрины. Охват и ограничения — docs/KASPI_AUTOMATIC.md. Не выдавать запущенный процесс за полный охват всех продавцов. Провайдеры отправки, реальные рассылки, автоматическое приглашение в мессенджеры и получение новых согласий не входят в этот этап. Развёртывание не должно отправлять сообщения клиентам.

## 5. Домен и пункт меню p1

- Выпустить и подключить сертификат для sales.overclockers.kz с автоматическим продлением; проверить HTTP → HTTPS и отсутствие циклов перенаправления.
- Добавить пункт «Рассылки» в штатное меню p1.overclockers.kz в существующем стиле. Использовать обычный переход на HTTPS sales; не встраивать приложение через iframe и не передавать токены в URL.
- Соблюдать существующие роли меню. Скрытие пункта для неподходящей роли дополняет серверную проверку доступа, но не заменяет её.
- Проверить desktop/mobile и активное состояние меню, если оно предусмотрено. Не менять другие пункты и не ломать имеющееся ПО p1.
- Если исходники p1 — отдельный репозиторий, оформить изменение там по его правилам и указать отдельный SHA/релиз.

## 6. Приёмка

Проверить и приложить отчёт без персональных данных:

1. SHA релиза и установка зависимостей; `manage.py check`, `manage.py check --deploy`, тесты contacts. Замечания deploy-check устранены либо обоснованы с конкретной защитой proxy.
2. Анонимный посетитель не видит контакты, статистику и выгрузки; прямые GET/POST к API тоже защищены. Неверная/просроченная сессия доступа не даёт. Вход, выход и CSRF работают через HTTPS.
3. Авторизованный пользователь видит клиентов, аудитории, фильтры, карточки, журнал и состояние источников; статические JS/CSS/favicon загружаются без ошибок.
4. Проверить импорт на отдельной тестовой БД и отсутствие дублей. Рабочие данные для тестов не удалять и не рассылать.
5. Подтверждено сохранение БД и статусов после рестарта приложения/обработчиков и перезагрузки сервера.
6. Пункт «Рассылки» на p1 открывает sales и не обходит вход. Проверены мобильное меню и TLS.
7. Есть автоматические резервные копии вне каталога релиза, установлен срок хранения и проверено восстановление; журнал не раскрывает персональные данные.
8. Перед включением источников сверены курсоры и исключён параллельный локальный сбор. Состояние worker heartbeat доступно оператору.

Зафиксировать адрес, SHA, службы и их команды управления, расположение настроек/данных (без секретов), способ обновления, отката и восстановления. При откате кода учитывать совместимость миграций; не откатывать БД с потерей новых записей автоматически. Сохранить скриншоты страницы входа и меню p1 без клиентских данных. Остановиться для проверки заказчиком.
