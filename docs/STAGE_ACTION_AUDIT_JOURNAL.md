# Журнал действий с рассылками

Дата: 12.11.2026. Меню «Журнал действий». После подэтапа остановиться для проверки заказчиком.

## Что записывается

- Создание и изменение черновика рассылки: название, версия, ID шаблона/отправителя/аудиторий и расписание до/после. HTML, тема, реквизиты SMTP, адреса получателей и весь HTTP-запрос не копируются.
- Подготовка очереди имитации, её первый запуск, пауза, продолжение, отмена и автоматическое завершение. Повторное действие без изменения состояния не создаёт ещё одну успешную запись.
- Создание и изменение сценария; запуск, пауза, продолжение и отмена его имитации.
- Запуск, пауза, продолжение и отмена репетиции; изменение порогов защиты и общей частоты; запись тестового результата доставки без копирования получателя и свободного текста результата.
- Автоматическая защитная остановка — отдельная запись от имени системы, с исходным и итоговым состояниями, причиной и снимком порогов. Если её вызвало действие оператора, сохраняется инициатор; одинаковый ID запроса связывает тестовое событие с остановкой.
- Известные отклонённые POST-действия журналируются отдельно с HTTP-результатом и общим объяснением. Они не выдаются за успешные изменения. Свободный текст ошибки/запроса и секретные URL не сохраняются.
- Обычные GET, опросы состояния, тики без перечисленных изменений и повторная пауза/отмена не создают успешных записей.

## Кто указан автором

1. Если сервер предоставил request.user с is_authenticated, используются ID и имя этой учётной записи.
2. Иначе используется серверная переменная WSGI REMOTE_USER, если она действительно установлена сервером. HTTP_REMOTE_USER, X-User и поля actor/user в JSON не принимаются за подтверждённого автора.
3. В текущей локальной копии авторизации нет. Оператор получает отдельный ID браузера в подписанной сервером HttpOnly/SameSite=Strict cookie; в журнале он явно помечен «Без авторизации». Можно указать локальную метку — она остаётся «Самоуказанной меткой» и не становится входом/подтверждением личности.
4. При смене метки прежние записи не переименовываются. Одинаковые имена в разных браузерах имеют разные ключи. Очистка/истечение cookie создаёт нового локального оператора.
5. Для фоновых/служебных вызовов без HTTP-контекста указывается «Система / служебный вызов». Автоматическая защита всегда указывает систему исполнителем и, при наличии, отдельно инициатора.

При подключении Django-входа middleware журнала следует размещать после middleware аутентификации и до CSRF. REMOTE_USER допустим только как доверенный серверный атрибут, не как перенаправленный пользовательский заголовок. Этот подэтап не добавляет авторизацию или новые права доступа.

## Хранение и согласованность

- Новые таблицы ActionAuditEntry и ActionAuditCampaign. Связь с рассылкой хранится ID, без изменения самой рассылки/контактов; изменение сценария связывается с прежними и новыми рассылками.
- У каждой записи фактическая серверная дата, автор и источник его идентификации, действие, объект/ID/название, результат, безопасные снимки до/после и ID HTTP-запроса. Виртуальная дата имитации при наличии находится в снимке и не подменяет фактическую дату записи.
- Запись об успешном изменении сохраняется в той же транзакции, что и действие. Если запись не удалась, изменение откатывается. Отклонённая попытка фиксируется отдельно после выхода из откатившейся транзакции.
- Автор берётся из контекста запроса через ContextVar; контекст сбрасывается после ответа и не переносится на другого оператора. Ошибки сохранения локальной метки не меняют её cookie.
- Подробности формируются из явно выбранных метаданных. Дополнительная фильтрация исключает чувствительные ключи. Пароли, HTML, содержимое запросов, заголовки авторизации, cookie, bearer-ссылки и IP не сохраняются.
- Редактирования и удаления записей в интерфейсе/API нет. Это прикладной журнал, а не криптографическая защита от владельца самой БД.
- Старые действия до включения подэтапа не восстанавливаются: их авторы неизвестны. Новые записи сохраняют название/состояние на момент действия.

## Интерфейс и API

- «Журнал действий» отделён от журнала сбора данных. Есть кнопки перехода из сценариев, репетиций и у конкретной рассылки.
- Фильтры: автор, действие, тип и ID объекта, связанная рассылка, результат, поиск названия/описания, период фактических дат включительно, порядок. Пагинация по 25 записей.
- «Подробности»: снимки до/после, автор, ID запроса и связанные рассылки. Строки выводятся как текст; HTML из названий/меток не выполняется.
- GET /api/action-journal — только чтение, no-store; POST /api/action-journal/operator меняет только неподтверждённую локальную метку с CSRF. Авторизованное имя меткой заменить нельзя.
- Журнал фиксирует состояние, но не включает SMTP и не запускает отправку. Изменения рабочей клиентской базы не являются побочным действием журналирования.

## Проверка заказчиком и локальный пример

Открыть «Журнал действий», фильтр «ID связанной рассылки» = 6.

- Проверочный черновик №6 создан и переименован в «Проверка журнала — версия 2» (версии 1 → 2). Аудитория «Сервисные центры», получателей 0, очереди нет.
- Проверочный сценарий №5 связан с этим черновиком; имитация №4 запущена, поставлена на паузу, продолжена и отменена. Новых писем не подготавливалось — действует общий лимит по тестовому email предыдущего подэтапа.
- Автор записей — «Проверка журнала (агент)», явно самоуказанная метка. Это проверочный пример, не утверждение о реальной учётной записи пользователя.
- Просмотреть «Подробности» изменения черновика и управления запуском. Обновление страницы сохраняет историю и метку; фильтры можно применить снова.

Предыдущие рассылки и сценарии не редактировались. Дополнительных SMTP-настроек и отправок нет.
