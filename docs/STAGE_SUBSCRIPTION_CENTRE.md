# Центр подписок — подэтап для приёмки

В меню добавлен раздел «Подписки», а в карточке клиента — «Подписки и согласия».

Хранение:
- EmailSubscription: нормализованный email, цель over_email_offers (email-акции OVER), тестовый/рабочий режим, состояние pending/confirmed/revoked, источник, URL и дата источника, примечание, текст и версия согласия, даты запроса/подтверждения/отзыва.
- SubscriptionEvent: история каждого запроса, подтверждения, отзыва и создания ссылки отписки, с копией текста согласия и происхождения. Через интерфейс нет изменения/удаления истории.
- SubscriptionToken: только SHA-256-хеш криптографически случайного токена, назначение, поколение, срок и состояние. Открытый токен выдаётся в ответе на создание ссылки и не возвращается в списке/истории.

Все новые запросы начинают с pending. Публичная ссылка показывает цель и текст согласия; подтверждение требует явной отметки и POST. Сам GET не подтверждает и не отзывает подписку. Срок подтверждения — 48 часов; новый запрос заменяет старую неиспользованную ссылку, отписка инвалидирует ожидающие подтверждения. Повтор применённого подтверждения не восстанавливает отозванное согласие. Ссылка отписки действует 365 дней; повтор при текущем revoked идемпотентен, после нового явного согласия старая ссылка позволяет снова отписаться.

Рабочая отписка:
1. Записывает revoked и историю.
2. Создаёт/обновляет глобальный EmailExclusion(reason=unsubscribe) и Address.suppression_reason, включая варианты регистра email.
3. Отменяет ожидающие подтверждения.
4. Учитывается в актуальном подсчёте рассылки, подготовке очереди и перед следующей попыткой обработчика.

Повторный запрос согласия не снимает запрет. Новое подтверждение снимает только отписку, сохраняя жалобы, окончательные ошибки и ручные/неизвестные ограничения. Ручное снятие причины unsubscribe через прежний интерфейс не обходит отзыв центра. Даже при устаревшем кеше Address очередь дополнительно проверяет рабочий отзыв центра. Повторный импорт Over-shop не снимает местный запрет.

Тестовый режим включён по умолчанию. Тестовое подтверждение/отписка меняют только тестовую подписку и её историю: не создают Address, не меняют реальные подписки/исключения/очередь и не подмешиваются в подтверждения отчёта готовности. Рабочий режим выбирается явно снятием отметки, с пояснением эффекта в форме.

Подтверждение ссылки означает действие её обладателя. На этом подэтапе письмо не отправляется, поэтому владение почтовым ящиком и доставка ссылки не доказаны автоматически. Это явно показано в центре и проверке готовности. Реальная отправка остаётся отключённой.

Интерфейс:
- создать запрос с источником и датой, получить ссылку, скопировать/открыть для проверки;
- фильтр email, состояния, режима, страницы по 25 записей;
- просмотреть историю с версиями и источниками;
- создать ссылку отписки;
- отдельно просмотреть ранее импортированные сведения Over-shop. Они не переписываются и не превращаются автоматически в новые согласия центра.

Публичная страница /subscription/<token>/ использует маскированный email, маркировку режима, POST с CSRF, no-store, no-referrer, noindex, CSP и отсутствие сторонних ресурсов. Добавлено прогрессивное выполнение формы через fetch с текущим CSRF: встроенный браузер при обычной форме передавал Origin:null, который Django правильно отклонял. Защита не отключалась, null не добавлялся в доверенные источники. Обычный POST формы остаётся рабочим для стандартного браузера. Тест подтверждает отказ для Origin:null и успешный запрос с корректным Origin/CSRF.

API:
- GET/POST /api/subscriptions — список/новый запрос;
- GET /api/subscriptions/<id> — данные и история;
- POST /api/subscriptions/<id>/unsubscribe-link — выдать ссылку отписки;
- GET/POST /subscription/<token>/ — просмотр/применение действия обладателем ссылки.

Ссылки локально строятся от текущего адреса приложения. После переноса задать SALES_PUBLIC_BASE_URL=https://sales.overclockers.kz и перезапустить приложение. Публичные страницы /subscription/ и статический /subscription-form.js должны быть доступны получателям, а административные API — за действующей защитой приложения. Настройки Host/HTTPS/CSRF прокси должны соответствовать публичному адресу. Токены в URL не следует включать в стороннюю аналитику. Интеграция ссылки {{unsubscribe_url}} в реально отправляемое письмо и RFC one-click обработчик для почтовых провайдеров остаются этапом подключения транспорта; этот подэтап обеспечивает пользовательскую веб-отписку по кнопке.

Проверка готовности учитывает подтверждённые рабочие записи центра, сохраняет сведения Over-shop как отдельное доказательство и отдаёт приоритет отзыву. Тестовые записи игнорируются. Проверка не утверждает, что тематика акции соответствует любому прежнему согласию.

Валидация: 123 теста центра, готовности, статистики, очереди, мастера, email-проверок/исключений, шаблонов, тестовой отправки, сегментов, таблицы и импорта Over-shop. Проверены хранение хешей/истории, GET без изменения, CSRF и Origin, обязательная отметка согласия, сроки и устаревшие ссылки, повторные действия, отзыв перед подтверждением, повторная подписка с сохранением других запретов, регистр email, невозможность ручного обхода, изоляция тестов, отсутствие SMTP/network вызовов, подсчёт и пропуск очередью отозванного адреса.

В браузере пройден полный путь на subscription-ui-check@example.invalid в тестовом режиме: запрос → подтверждение → ссылка отписки → отписка → история с датами. Запись оставлена для приёмки, текущий статус revoked. Реального Address с этим email нет; пользовательская база не менялась. Письма не отправлялись. Перед миграцией 0029 сделана data/backups/before-subscription-centre-*.sqlite3, quick_check=ok.

Для приёмки: «Подписки» → оставить тестовую отметку → создать запрос для своего тестового адреса → открыть ссылку, отметить согласие и подтвердить → обновить список → создать ссылку отписки → открыть и нажать «Отписаться» → посмотреть историю. После подэтапа остановиться для проверки пользователя.
