# Автоматические сценарии активных и пассивных аудиторий — имитация

Дата: 12.11.2026. Меню: **Сценарии**. Реальная отправка отсутствует. После подэтапа остановиться для проверки заказчиком.

## Сценарий

- Название и версия сохраняются в БД.
- Условие входа — виртуальная группа «Активные» либо «Пассивные» из существующего расчёта тестовой активности.
- Настраиваются окно активности (1–730 дней), минимум разных доставленных писем (1–20) и ожидание после последней доставки (0–180 дней). Ожидание не превышает окно.
- Дополнительное условие по открытиям: любые / без открытий / есть открытия. Все условия объединяются через И.
- Активность определяется переходами; открытия сами по себе не доказывают активность или прочтение.
- Тестовая отписка или окончательная ошибка не допускают вход. После входа эти события останавливают оставшиеся шаги. Получатель, утративший нужную группу/условие открытий, выходит из запуска.
- Источники: отдельная демонстрация `ActivityTestEvent` либо `CampaignTestEvent` с выбранным набором/рассылкой. Живые клиенты и рабочая статистика источниками не являются. Кнопка «Подготовить тестовую аудиторию» идемпотентно наполняет прежний отдельный набор активности.

Сценарий содержит 1–5 шагов. Для шага выбираются сохранённая рассылка как источник письма/отправителя и задержка 0–43200 минут. Реальные получатели выбранной рассылки в сценарий не импортируются. Первый срок считается от входа; следующий — от времени предыдущего фактически имитированного шага. Минимальный интервал может увеличить задержку.

При запуске фиксируются версия сценария, условия, задержки, ограничения и копии писем/отправителей всех шагов. Если у выбранной рассылки есть очередь, используется её сохранённая копия. Последующее редактирование сценария, шаблона или рассылки не подменяет открытый запуск. Новая версия применяется при следующем запуске после отмены старого. Завершение шагов у текущих участников само по себе не закрывает работающий запуск: он может ждать новых участников.

## Ограничения частоты

Для каждого сценария задаются:

- минимальный интервал: 1–10080 минут, по умолчанию 1440;
- максимум за скользящие 24 часа: 1–10, по умолчанию 1;
- максимум за скользящие 7 дней: 1–30, по умолчанию 3; недельный максимум не меньше суточного;
- ожидание повторного входа в новый запуск этого же сценария: 1–365 дней, по умолчанию 7.

Каждый шаг проверяет свои ограничения по всей истории **имитаций** данного нормализованного email во всех сценариях, включая отменённые запуски. При разных настройках у двух сценариев каждый применяет собственные пределы к общей истории; это не отдельная единая политика транспорта. Границы 24 часов и 7 дней исключают событие, срок которого ровно истёк. При ограничении вычисляется следующий срок проверки, причина записывается в журнал. Отмена не очищает историю частоты.

Один получатель проходит конкретный запуск только один раз. После завершения/выхода он автоматически не возвращается в тот же запуск. Для повторного прохода нужен новый запуск после отмены прежнего и окончания срока повторного входа. Срок считается от предыдущего входа, включая вышедшие/отменённые записи; повторная попытка не сбрасывает ограничения.

## Часы и обработка

Все запуски используют общие сохраняемые часы `AutomationSimulationClock`. На старте они равны текущему времени. Доступны «Обработать сейчас», «+1 час», «+1 день», «+7 дней». Назад часы не переводятся.

Обработка выполняет расчёт на текущую виртуальную дату, принимает новых подходящих участников, перепроверяет ожидающих и имитирует допустимые шаги. При скачке времени пропущенные моменты **не проигрываются задним числом**: просроченный шаг рассматривается на новой дате; дальнейшая задержка начинается от фактической даты имитации. Будущие относительно часов тестовые события не учитываются.

Пока экран открыт, раз в 15 секунд выполняется цикл обработки при наличии работающих имитаций, без продвижения часов. Для будущих задержек часы нужно продвинуть вручную. Без браузера доступен однократный серверный цикл:

```powershell
.venv/Scripts/python.exe manage.py process_automation_simulations
.venv/Scripts/python.exe manage.py process_automation_simulations --advance-minutes 60
```

Постоянная служба и привязка сценариев к реальному времени не устанавливались. Команда не подключается к SMTP/API провайдера. Все мутации имитации сериализуются блокировкой общих часов. Уникальные ограничения БД исключают повтор участника в запуске и повтор шага. Отдельный ограничитель разрешает не больше одного работающего/приостановленного запуска сценария.

Есть пауза, продолжение и отмена. Пауза сохраняет сроки, однако общие часы других запусков могут двигаться. Продолжение заново проверяет условия и частоту. Отмена останавливает ожидающих участников и сохраняет журнал. Завершившие все шаги участники остаются завершёнными; сам работающий запуск может ждать новых подходящих получателей.

## Данные и интерфейс

Миграция `0034` создаёт `AutomationScenario`, `AutomationSimulationClock`, `AutomationSimulationRun`, `AutomationSimulationMember`, `AutomationSimulationAction`, `AutomationSimulationLog`.

Шаг записывается только в `AutomationSimulationAction` и журнал решений. Он не создаёт `TrackedMessage`, `CampaignTestEvent`, отправку, доставку, открытие или отписку. Не меняются `Address`, `Client`, `Contact`, рабочие подписки/исключения, реальные метрики, аудитории или существующая очередь рассылки. Даже совпадение тестового email с реальным адресом этого не меняет.

В интерфейсе: список сценариев, редактор правил/шагов, запуск имитации, общие часы, состояние запуска, участники и журнал решений. Журнал содержит причины невхода, вход, имитацию шага, частотное ограничение, ожидание повторного входа, выход/исключение и управление запуском. Причины первоначального невхода и ожидания повторного входа пишутся один раз на получателя/запуск; при последующей квалификации вход возможен.

Фильтры журнала: запуск, email, решение, порядок времени; страницы по 25 записей. Список участников показывает первые 100 соответствующих поиску email. В списках — последние 200 сценариев/запусков. Карточка «Исключены после входа» относится только к бывшим участникам, а не ко всему тестовому источнику.

Мобильный экран до 700 px использует карточки таблиц, одну колонку полей, шрифт полей 16 px и кнопки не менее 44 px. Данные, конфигурации и журнал сохраняются при перезапуске; вкладка восстанавливает раздел. Несохранённые поля редактора и фильтры в БД не сохраняются. После открытия по умолчанию показывается последний запуск.

Предел пилота: до 1000 получателей/10 000 тестовых событий в одном источнике, до 10 открытых запусков, до 500 имитированных шагов за цикл. Необработанные из-за бюджета участники остаются ожидающими для следующего цикла. Слишком большой источник отклоняется с откатом транзакции; часы/шаги не изменяются частично.

## API

- `GET/POST /api/automations`, `GET/POST /api/automations/<id>` — список/версионное сохранение.
- `POST /api/automations/<id>/run` — новый запуск с актуальной `revision`.
- `GET /api/automation-simulation?run_id=...&query=...&kind=...&direction=...&page=...` — состояние/журнал.
- `POST /api/automation-simulation` — `action=tick|advance|pause|resume|cancel`; для advance — `minutes` (0–10080), для управления — `run_id`.

Мутации требуют `mode=simulation`, `test_only=true`; `send=true` и рабочий режим отклоняются. API остаётся за существующей авторизацией приложения при развёртывании; публичные обработчики трекинга не используются этим модулем.
