# Автозапуск Sales на сервере — задание агенту

Подготовлено 13.11.2026. Конфигурация рассчитана на Linux с systemd и существующий
HTTPS reverse proxy. Реальная ОС, пути и служба сервера пока не проверены.
На сервере ничего не установлено. SMTP и реальная отправка запрещены на всём этапе.

## 1. Обследование и подготовка

Сначала прочитать `docs/DEPLOYMENT_AGENT_TASK.md` и серверный AGENTS.md. Проверить
ОС, менеджер служб, текущий путь Sales, пользователя, Python, БД, reverse proxy,
занятые порты и действующие службы/контейнеры/таймеры. Зафиксировать текущий SHA.
Если Sales уже управляется systemd, адаптировать существующую службу, не создавать
параллельный экземпляр. Если используется Docker или другая ОС, данный unit не
устанавливать вслепую: адаптировать к фактической инфраструктуре и показать результат.
Не менять службы Госзакупок и p1, общие конфиги или настройки чужих приложений.

Примеры ниже предполагают `/opt/over-sales/current`, пользователя `sales`,
службу `over-sales.service`, данные `/var/lib/over-sales`. Заменить пути и имя службы
согласованно во всех файлах, если сервер уже использует другие. Перед развёртыванием
проверить, что выбранный SHA ветки main содержит эти файлы и весь зависимый код.

Сохранить конфиги текущей службы/proxy и приватного окружения. Сделать проверенную
резервную копию БД и всего каталога данных, включая импорты Over-shop, курсоры,
согласия, исключения и учётные записи. Для SQLite остановить всех писателей на время
копирования (включая сборщики) либо использовать SQLite online backup; не копировать
один файл работающей WAL-базы. Сохранить прежний постоянный DJANGO_SECRET_KEY.
Не печатать ключи, пароли, токены и содержимое клиентской базы в отчёт или Git.

## 2. Файлы и окружение

Использовать системный Python 3.11+ на Linux; создать серверную `.venv` и установить
`python -m pip install -r requirements-server.txt`. Windows `.venv` не переносить.
Код и окружение должны читаться пользователем службы, но не быть доступны ему для
записи; служба запускается без root. Создать служебного пользователя без входа,
если такого ещё нет. Не создавать новую БД поверх существующей.

Создать каталог данных с владельцем службы и правами 0700. При переходе с
`<проект>/data` перенести всё содержимое в `/var/lib/over-sales` при остановленных
писателях, проверить владельца и количество записей. Исходную копию сохранить
до приёмки. Для PostgreSQL сохранить существующие POSTGRES_*: миграция SQLite в
PostgreSQL не выполняется сменой окружения.

Скопировать `deploy/sales.env.example` в `/etc/over-sales/sales.env`, владелец root,
права 0600. Это не shell-скрипт: не выполнять `source` и не хранить в репозитории.
Заполнить постоянный DJANGO_SECRET_KEY (случайный, минимум 50 символов) только для
новой установки; при обновлении сохранить прежний. Указать точные hosts, внешний
HTTPS origin и абсолютный каталог данных. Новые учётные SMTP/Servercore не нужны.
`mailer.production` принудительно отключает SMTP и использует dummy email backend,
даже при старом SALES_SMTP_ENABLED=1. Не менять этот запрет.

Unit жёстко задаёт `/var/lib/over-sales`; EnvironmentFile может переопределять
Environment, поэтому SALES_DATA_DIR в env и StateDirectory/ReadWritePaths в unit
должны совпадать. Для команд обслуживания использовать то же окружение и профиль
`mailer.production`, не локальные настройки. Для безопасного выполнения команды
с root-only EnvironmentFile можно использовать одноразовый systemd unit:

```bash
# Пример ПОСЛЕ подстановки фактических путей; приложение и писатели остановлены.
sudo systemd-run --wait --pipe --collect --uid=sales --gid=sales \
  --working-directory=/opt/over-sales/current \
  --property=EnvironmentFile=/etc/over-sales/sales.env \
  --setenv=DJANGO_SETTINGS_MODULE=mailer.production \
  /opt/over-sales/current/.venv/bin/python manage.py check --deploy --fail-level ERROR
```

После backup той же командой заменить `check ...` на `migrate --noinput`, затем
`migrate --check`, затем `sync_app_notifications`. Миграции выполняются один раз
при обновлении, не при каждой загрузке ОС. Данные не загружать из демонстрационных
fixtures. Существующие пользователи и пароли сохраняются. `prepare_auth_setup`
нужен только для новой пустой базы без пользователей; владелец сам вводит код и
пароль через HTTPS. Код и пароль в отчёт не включать.

## 3. Служба и proxy

Адаптировать `deploy/systemd/over-sales.service` к фактической установке. Проверить:

```bash
sudo systemd-analyze verify /etc/systemd/system/over-sales.service
sudo systemctl daemon-reload
sudo systemctl enable --now over-sales.service
sudo systemctl is-enabled over-sales.service
sudo systemctl status over-sales.service --no-pager
```

Запускается Gunicorn через `mailer.wsgi`, без Django runserver. Перед стартом —
проверки конфигурации и наличия миграций, без изменения схемы. При сбое — повтор
через 5 секунд, максимум 5 попыток за 5 минут; затем исправить причину и выполнить
`systemctl reset-failed over-sales.service`, `systemctl start over-sales.service`.
Штатная остановка через `systemctl stop` не вызывает самовосстановление.
Журнал — `journalctl -u over-sales.service`; не публиковать необработанные логи с
данными клиентов. Начальная настройка: один worker, четыре потока для SQLite.

Порт 8173 доступен только на loopback. Проверить отсутствие другого экземпляра и
запрета со стороны SELinux/AppArmor; не отключать защиту сервера целиком.
`deploy/nginx-sales-location.conf` — фрагмент для существующего HTTPS vhost Sales,
не полноценная замена nginx.conf. При другом proxy адаптировать аналогично:
перезаписывать Host и X-Forwarded-Proto, не доверять клиентским forwarded headers,
отключить запись полных URL с токенами. Не создавать второй location / и не
раздавать весь каталог проекта/data. TLS и перенаправление HTTP→HTTPS сохранить.
Перед reload выполнить `nginx -t` или проверку фактического proxy.

SECURE_HSTS_SECONDS пока 0 до проверки сертификата, поэтому `check --deploy` может
дать предупреждение W004. После приёмки TLS отдельно настроить HSTS. Не включать
includeSubDomains/preload для всего overclockers.kz без отдельного решения.

Этот подэтап запускает только веб-приложение. Имеющиеся сборщики и проверки email
сохранить с их прежними интервалами/паузами, тем же каталогом данных и окружением;
не запускать дубликаты. Новые worker-службы, отправляющие SMTP, не создавать.

## 4. Приёмка и откат

Проверить внешний HTTPS, вход владельца, клиентские счётчики, шаблоны, аудитории,
согласия, роли, доступ к API и мобильное меню. Локальный DB-зависимый probe:

```bash
curl --fail --silent --show-error \
  -H 'Host: sales.overclockers.kz' -H 'X-Forwarded-Proto: https' \
  http://127.0.0.1:8173/api/auth/session
```

Анонимный probe не должен открывать клиентские данные; `can_send` должен быть false.
Проверить, что порт 8173 не слушает публичные интерфейсы. Зафиксировать контрольные
количества/хеши без выгрузки персональных данных (`scripts/acceptance_snapshot.py`).
Затем проверить `systemctl restart`: вход/данные сохраняются, процесс один.
Для проверки восстановления можно выполнить контролируемый сбой только службы
Sales (`systemctl kill --signal=SIGKILL --kill-whom=main over-sales.service`) и
убедиться в новом PID/здоровом probe. Реальных писем не отправлять.

Настоящую перезагрузку общего сервера выполнять только в согласованное владельцем
окно, учитывая соседние приложения. После неё проверить enabled/active, новый
boot ID, сайт снаружи, те же данные и отсутствие дубликатов. Если reboot не сделан,
отметить пункт неподтверждённым; restart процесса не заменяет reboot сервера.

При неудаче остановить новую службу, восстановить прежние unit/proxy/релиз и его
окружение, выполнить daemon-reload и проверку proxy. Не запускать одновременно
старую и новую службу на одной БД. Если схема изменена несовместимо — восстановить
проверенный backup только при остановленных писателях; не удалять новую БД до
разбора. Сохранить SMTP выключенным при откате.

Отчёт агенту: SHA, ОС, реальные пути и имя службы, enabled/active, проверки DB и
прав, восстановление после сбоя, результат reboot или причина пропуска, отсутствие
SMTP/реальной отправки. После этого остановиться для проверки владельцем.

Официальные справки, проверенные при подготовке:
[Gunicorn deployment](https://gunicorn.org/deploy/),
[релиз Gunicorn в PyPI](https://pypi.org/project/gunicorn/).
